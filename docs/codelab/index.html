Step 1 of 13 · 3 min

Overview

What you'll build, what you need, how long it takes

You'll take one sentence from a chief information officer (CIO) and follow it, one working session at a time, to tickets a team can build from. The example is Heron, a made-up desk helper for Marlowe, a company of 4,200 people. The sentence is real, from the demo plan:

The CIO wants "a desk helper for Mac and Windows that sets up in two minutes, quietly watches your meetings, email and documents, and tells you what matters each morning".
  • What you'll build: a plan in a folder of Markdown pages: goals, open questions, the apps involved, what the business needs, two releases, the work for each team, and tickets.
  • What you need: Claude Code, git, and a folder you can write to. Vela runs on Python 3.9 or later and brings its own copy of PyYAML, so nothing else to install. You play the solution lead, the person who owns the plan.
  • How long: about 161 minutes on a first run, the sum of the rough times on each step. A real session with real answers can run longer.
  • How to read this: each step shows what you type, what Claude asks you, and what you should see. Use the arrow keys or the buttons to move. The step list above jumps anywhere.
How to tell a real excerpt from an example

What Claude asks is an example of what the skills tell it to ask. Your questions will differ, because Claude reads your plan first. Everything under "What you should see" is real: it comes from the Heron demo plan, or from vela commands run on a copy of it.

The Heron plan was made by vela's session simulator, so it shows the format and the real check output. It isn't evidence from a real initiative. Its handles read @sim-lead.

Checkpoint

You can say, in one sentence, what you'll have at the end: a plan that goes from the CIO's sentence to tickets, with the reason for every step kept.

Stuck?

Nothing to run yet, so nothing to get stuck on. If a later step doesn't match this page, check that you're on the step you think you're on: the address ends in #step- and a number.

Step 2 of 13 · 5 min

Install vela

Add the plugin to Claude Code and check the machine

Two commands in Claude Code add vela. Then you ask Claude to check that the machine has what vela needs.

You type

In Claude Code:

/plugin marketplace add smalls257/vela
/plugin install vela@vela

Then ask Claude: "Run vela doctor."

Claude asks you

Nothing yet. Claude doesn't ask you anything in this step.

What you should see

vela doctor prints one line per item, run in an empty folder on a Mac:

ok    Python 3.14.4 (/opt/homebrew/opt/python@3.14/bin/python3.14)
ok    PyYAML 6.0.3, bundled with the plugin (nothing to install)
ok    git version 2.50.1 (Apple Git-155)
ok    node v26.11.1: vela check parses the diagrams
ok    claude command found: the explorer's Ask Claude box works
info  vela plugin 0.5.0
vela doctor: ready.

Checkpoint

The last line reads vela doctor: ready. Your versions will differ. A line starting optional is fine: it says what that item would add.

Why this step

Vela checks things (vela check) and writes pages. Both need a known setup on your machine, and the doctor is the one place that says what's missing. The idea behind the rest, that a claim should be checkable by something other than Claude's say-so, is on the trust page.

Stuck?
  • A line that says optional isn't a failure. It names what the item adds and the one command that gets it.
  • vela: <folder> has no .vela.yaml, so it is not a vault. Run vela from the vault root or pass --vault. means you ran a plan command outside a plan. That's expected here. The next step makes the plan.
  • The repo is public, so installing needs no access grant. Git should be signed in to GitHub, which gh auth login does.

Step 3 of 13 · 3 min

Start a plan

Make a folder, open Claude Code in it, and let vela start the plan

A plan is a git repository of Markdown pages, one folder per initiative. You make an empty folder and ask for a first session. If there's no plan yet, Claude offers to start one, and that runs vela new.

You type

In a terminal:

mkdir heron-desk
cd heron-desk
claude

Then in Claude Code: /vela:dump. If you'd rather start the plan by hand: vela new --title "Heron Desk".

Claude asks you

Claude asks two things:

There's no plan in this folder yet. Want me to start one? What short name should the initiative go by, a few words as you'd say it to a colleague?

If vela can't find your GitHub handle, Claude asks for it once.

What you should see

vela new, run for real with the handle @solution-lead:

vela new: started INI-001 'Heron Desk' for @solution-lead in .../heron-desk: 48 files, committed 2dae834: Start the plan.
vela check: 0 errors, 0 warnings.
Left for a person: a GitHub repository, the required check, Obsidian (see README.md).

Then vela next, which suggests what to do:

vela next: for the whole plan: no app page exists yet, so start by getting everything known written down (/vela:dump, a brainstorm), or by reading the existing sources (/vela:discover).

Checkpoint

The folder holds 01-goals.md, 11-unknowns-and-risks.md, a README.md and about 45 more files, and vela check reports 0 errors. git log shows one commit, "Start the plan".

Why this step

Everything vela knows lives in plain files in git, so you can read, review and undo it. Starting with vela new instead of copying a template means the first commit holds only the plan's own files. More on why plans are files with checks, not documents: the problem page.

Stuck?
  • vela new refuses a folder that already holds a plan, a folder inside another plan, and a folder with plans below it. Pick an empty one.
  • To put a plan inside a repository that already holds others: vela new --vault projects/heron --title "Heron rollout".
  • If it asks for your GitHub handle, give it once: vela new --title "Heron Desk" --handle @your-handle.
  • The README the new plan carries lists what's left for a person: a GitHub repository, the required check, and Obsidian if you use it. None of it blocks the next step.

Step 4 of 13 · 20 min

Dump

Get everything out of your head, ideas and worries and unknowns alike

A dump is the first session. You talk, Claude writes each point down as its own numbered line in your words, and pushes back on nothing. Nothing reaches the plan's pages until you close the session.

You type

In Claude Code, in the plan folder:

/vela:dump

Say the CIO's sentence, then what you're unsure of. When you're done: /vela:close.

Claude asks you

Claude adds one "what if" per idea and labels it as its own. After a while it runs a pre-mortem:

Imagine it's six months from now and Heron has failed. What went wrong?

Then it shows the questions nobody has asked yet, and you choose which to take.

What you should see

Captures from the Heron dump, after close. Each line says who said it, and where it went:

- [thought] (solution lead) The CIO wants "a desk helper for Mac and Windows that sets up in two minutes, ..." → keep: [[01-goals#Goals|goals]] (inkling) ^c01
- [worry] (solution lead) I've been made solution lead and it's a blank page. I don't know where to start. → keep: UNK-052 (open) ^c02
- [idea] (claude) What if the morning briefing came first and alone, built from just the calendar, ... → park ^c04
- [unknown] (solution lead) The CIO just gave me the one-liner and nothing since. Honestly not sure what morning they were picturing. → keep: UNK-055 (open) ^c08

Checkpoint

You have a session record under sessions/ with your lines in it, and Claude's ideas are labeled (claude). After close, each line ends in keep, park or drop, and every unknown you kept has an owner.

Why this step

The vague intent becomes a recorded unknown with an owner, so it can't turn into a decision nobody made. Dump is the first rung of the ladder. The plan marks the CIO's sentence inkling, a hunch: see how sure each thing is.

Stuck?
  • I said something and it isn't on any page yet. That's right: a dump writes nothing outside sessions/ until /vela:close.
  • E207 means an ID reference resolves to nothing, usually a mistyped UNK- number in a capture.
  • E201 means a link goes to a page that doesn't exist. Real output: 01-goals.md:124: E201 [[no-such-page]] links to a page that does not exist. Fix: Fix the basename, or create the page.

Step 5 of 13 · 20 min

Discover or import

Read what already exists, and write down only what a source says

Pick one. If you have documents (a brief, a tenant note, a survey), run Discover. If an initiative is already under way in documents, code and tickets, run Import, which shows a map of what it found before writing anything.

You type

Put the documents in the plan folder, then:

/vela:discover

or, for work already under way: /vela:import

Claude asks you

Claude asks you to rank the documents, then reads back what it thinks exists, in groups of about five, naming each source and saying whether it describes today or a plan:

1. Partners get a nightly file of changed bookings (the partner guide, what runs today). 2. Guests can rebook on their phones by Q4 (the 2026 roadmap deck, a plan, so not decided yet).

>

Do these hold?

If two lines disagree, it says so aloud and offers one open question naming both sides.

What you should see

Two Heron sources in the Library, one that exists today and one that is only intended:

| SRC-006 | Microsoft 365 tenant note | IT endpoint lead | 2026-10-02 | exists | document | ...
| SRC-007 | CIO brief on Heron | CIO | 2026-09-30 | intends | document | ...

They disagreed, and discover didn't pick a side:

- [unknown] (claude) The CIO brief says staff install the helper themselves, while the tenant note says staff cannot install software and everything is pushed from Intune or Jamf. Two sources disagree; the CIO and the IT endpoint lead are asked. → keep: UNK-086 (open) ^c06

Checkpoint

Every fact the session wrote cites a source in sources.md. A line from an intends source is an assumption, not a fact. Any clash is an open question with an owner.

Why this step

Nobody designs anything before finding out what exists. A fact needs a source, and Claude's general knowledge is never a source: see Discover and Import and a fact needs a source.

Stuck?
  • E304 means a fact has no source. Add the source row to sources.md, or set the line back to an assumption.
  • E307 and E309 mean a Library row has a bad type, or neither a stored file nor a location.
  • Documents in .inbox/ stay on your machine. Git ignores that folder, so company files aren't committed unless you agree to keep one.

Step 6 of 13 · 15 min

Shape

Two or three options to react to, and a pick that stays not decided

Shape gives you something concrete to react to. Claude lays out two or three options, never one and never more than three, and records the ones you turn down with the reason. What you pick stays "not decided yet" until a grill decides it.

You type

/vela:shape the first release

Claude asks you

Each option comes with what it does, costs and rules out, and what must be true for it to work. Then:

Which of these would you pick, and what would make you drop it?

For the pick, Claude takes each "what must be true" line in turn: is it known (with a source), a belief, or an open question for someone?

What you should see

The Heron strategy page, with the options and the reasons for turning two down:

- **Options considered:** Follow-ups owed after client calls (picked); morning calendar briefing on the laptop: rejected, Sam's team would only use Heron if it works on client calls; briefing by invitation: rejected, people who have to hand things over by hand won't, so it is dead.

The page is still at inkling, so the lead recorded an override to go on to requirements anyway:

- **Override:** "If 04-solution-strategy.md is not decided, say so: requirements written against it may be written again." by @sim-lead on 2026-10-19: Go on—requirements will show us what questions the grill needs to ask anyway.

Checkpoint

The strategy page has an Options considered line naming what you picked and each option you rejected with its reason. Its state is still not decided.

Why this step

Giving someone three choices gets better reactions than asking for requirements cold, and the rejected options keep the reason on the page. See Shape. The override is how you're never blocked: you can go on, and the rule you set aside is named on the page (overrides).

Stuck?
  • vela check --gate shape warns W806 for each question still marked assumed. A warning, not a stop: you may go on.
  • E303 means a page says decided with no grill behind it. Set it back to assumption.

Step 7 of 13 · 30 min

Requirements and boundary

What the business needs with no app named, then where the apps divide

Two sessions, in order. Requirements says what the business needs, once, naming no app, screen or technology. Boundary then turns a direction into apps: two or three ways to cut it, then one page per app.

You type

/vela:requirements
/vela:boundary

Claude asks you

Requirements takes one requirement at a time, with its recommended answer, and pushes on the edge cases:

What should happen when a call has one person on it who hasn't opted in? I'd say no summary at all, for anyone. Does that hold?

Boundary asks you to pick between its cuts, and says what each rules out.

What you should see

A requirement from the Heron plan. It names no app:

### CAP-023.FR1 Summarize only fully opted-in calls

- **State:** assumption
- Heron summarizes a call only when every participant on it has opted in to Heron.
  - Trace: UNK-093
- A call with even one participant who hasn't opted in gets no summary.

The boundary cut it to four apps, and the decision keeps the cuts it rejected:

| Three apps, with the admin view inside the Heron service | The works council's view and the reading service would ship and fail together. |
| Two apps, with consent inside the Heron service | The consent record is lost with the service, and the identity team's registration review has no seam. |

Checkpoint

There's a capability page with numbered requirements, each with criteria and a trace to what it depends on. There's a page for each app saying what it does and doesn't do. vela status lists the apps at the stage boundaries.

Why this step

Naming apps too early freezes a guess. Requirements come first so the cut can be argued against something. See Requirements and Boundary. Allocation, the step that gives each requirement an owning app, comes next in a full run: see What's next. The Heron demo plan stopped before it, and vela check says so for each requirement.

Stuck?
  • W505: a requirement is not decided yet and no app has taken it. Real output: Fix: Run /vela:allocate CAP-022, or add a row for CAP-022.FR1 to the app page that delivers it. The Heron plan shows nine of these.
  • E350 means a flow step names a sender or receiver its contract doesn't join.
  • E103 means a page is missing a required frontmatter field.

Step 8 of 13 · 15 min

Grill a decision

A grill is the only way something becomes decided

A grill is a working session where vela asks you questions one at a time until a part of the plan is settled. Only a grill can mark something decided, and only after your explicit yes.

You type

/vela:grill Admin console

Name the thing by its name, as the plan calls it.

Claude asks you

Each question comes with a recommended answer and a reason. Claude picks an edge case, not the happy path, and reads back what it would write:

Record consent: the desktop agent asks for both choices, the calendar and the chosen folder, and keeps each with the time it was given. If saving doesn't answer within two seconds, the agent says "Couldn't save your choice, so nothing was switched on" and asks again at the next start. That's what I'll write as decided. Right?

Only a plain yes counts. "Looks fine" doesn't.

What you should see

A decision from the Heron plan. The state is decided, and the page links the grill session that decided it:

state: decided
...
## Decision
The Admin console is its own app. It shows what the Consent and identity service holds and keeps no consent record of its own.
...
- **Decision:** [[2026-10-19-tracer-slice-first-path]]

Checkpoint

The item says decided and has a **Decision:** line pointing at a grill session. No open question blocks it.

Why this step

Without a gate, "decided" means whoever wrote it last. Here it means a named person said yes in a session that's on record. See how only a grill decides and what Claude may never do.

Stuck?
  • E303 decided with no grill. Real output: 04-solution-strategy.md:6: E303 solution-strategy is decided, but no **Decision:** bullet links a Grill session. Fix: Add '- **Decision:** [[<grill session>]]', or set the state back to assumption.
  • E316 decided while an open question blocks it. Answer the question first, or override the rule and say why.
  • You can always override. Claude says once what the rule protects, does what you asked and records your reason. It never blocks you.

Step 9 of 13 · 20 min

Releases and epics

When people first see it, what must hold that day, and each team's work

Releases come first: a date someone outside the team will see, and the requirements, or only some of their checks, that must hold that day. Epics then cut the work for each team, each with a "done when" a tester can check.

You type

/vela:releases
/vela:epics

Claude asks you

Releases asks one question at a time, date first:

When does anyone outside the team first use this, and who are they?

Then, requirement by requirement: must be there, can wait, or only part. Epics reads back the checks a tester will use, with a recommended tightening, for example "within two minutes" in place of "as soon as it can be built".

What you should see

The first Heron release. Some requirements only come in part:

## Release one: February pilot, Client Delivery London
- **Target:** 2027-02-02
- **State:** assumption
- **Slices:** SLC-005

| Close a follow-up | AC1, AC2, AC3 | AC4 and AC5 in release two, no date yet |

vela releases brief says it back:

- Release one: February pilot, Client Delivery London: aimed at February 2, 2027, not decided yet; slices on by then: A person gets their first follow-up list; ...
- Release two: what the pilot leaves for later: with no date yet, early idea; slices on by then: none; ...

Checkpoint

04b-releases.md names each release with a date or "no date yet", and says which requirements it delivers. Each epic lists its owning team and its "done when" checks.

Why this step

Nothing waits for a release; a release is a promise about a date. Writing it down is how a team learns that a requirement it thought was whole is only half due. See Releases and Epics.

Stuck?
  • W343 a requirement isn't decided yet and no release delivers it, so nothing says when it ships. Add it to the release that will deliver it, once nothing holds it back.
  • W347 a slice passes through an app that the release delivers no share of, so its journey can't run end to end by that date. The Heron plan has seven of these.
  • E805 a high-severity question is still pending at the epics gate. Answer it, or override with a reason under ## Question ledger; the error then prints as W805.

Step 10 of 13 · 3 min

Open the dashboard

The whole plan on one page you can present from

The dashboard is one offline HTML page drawn from the plan: the map of apps, each journey played step by step, who holds each open question, and where each app stands. It never changes a page.

You type

/vela:explore

or by hand: vela explore

Claude asks you

Nothing needed from you. Claude builds the page and opens it in your browser.

What you should see

The last line of vela explore on the Heron plan:

vela explore: wrote dashboard.html for INI-001 Heron: 4 apps, 6 contracts, 49 unknowns, 3 epics, 1 flows, as of 2026-10-22.

Checkpoint

You have dashboard.html at the plan's root, and clicking an app in the map opens its detail. The top says when the page was built.

Why this step

Under pressure, you need to find a topic and the apps it touches in about two clicks. The dashboard is for a live call; vela view builds the reading copy you email. See the dashboard.

Stuck?
  • The page says at the top when it was built. If it looks old, build it again; an unchanged plan rebuilds to the same bytes.
  • The "Ask Claude" box needs the claude command, which vela doctor checks.
  • vela view --out ~/Desktop/<name>.html builds the reading copy. It works offline and can't run page script.

Step 11 of 13 · 10 min

Hand off an app

Give an app to its team lead, with what isn't settled said out loud

When an app is ready for its team, you grill its handoff. It records what the team lead accepts, and what isn't settled yet, so nobody finds out later.

You type

/vela:grill the Desktop agent's handoff
/vela:close

Claude asks you

Claude reads back what the team is taking and what stays open, then asks:

Hand the Desktop agent to its team lead, with these items not decided yet and this question still open. Yes to send it?

What you should see

The handoff record Heron wrote. It lists what the team accepted:

- **App:** APP-desktop-agent
- **Commit:** 8e30fa9
- **Items:** 7
| APP-desktop-agent | app | 05-building-blocks/desktop-agent-building-blocks.md | assumption | ec4c4412c80b |
| CON-021 | consumes | ... | assumption | 8eed90afa9ff |

Later, vela handoff verify says what moved since:

vela handoff verify APP-desktop-agent: since Desktop agent was handed off on 2026-10-19 at 8e30fa9, 2 things changed, 2 added and 0 removed.
changed: app Desktop agent (APP-desktop-agent): its wording changed
added: epic Setting Heron up in two minutes (EPC-038), ..., draft

Checkpoint

handoffs/<app>.md exists, the app page says who has it and when, and a "Not settled at handoff" list says what's still open.

Why this step

A team that finds an undecided contract halfway through blames the plan. A team told on day one plans around it. See handoff, challenge and answer.

Stuck?
  • W386 an item in the handoff list isn't decided. Decide it in a grill, or tell the team it isn't settled.
  • W388 the handoff record points at a commit this repository doesn't have. Commit your changes, then vela handoff <app> --replace.
  • vela handoff verify exits 1 when something the team accepted has changed. That's a signal, not a failure.

Step 12 of 13 · 15 min

Write tickets

The team lead designs and breaks down the work; vela turns it into tickets

The team lead takes it from here, in three sessions on the app's own branch: a technical design, a breakdown into stories and tasks, and the ticket list. You can run them yourself to see the result.

You type

/vela:design Desktop agent
/vela:breakdown
/vela:tickets

Claude asks you

Tickets first checks the plan against the plan, then asks:

I'd write one Markdown file with a section per story. Or a CSV for Jira import. Which one?

What you should see

vela tickets check on the Heron plan:

Needs fixing: Story S-06 isn't linked to an epic's acceptance criterion or to a requirement the app owns, so nothing in the plan says when it's done
...
10 stories, 49 tasks, 3 flagged

The ticket file it writes:

## S-01 A person sees a first follow-up list
- Slice: tracer, SLC-005 A person gets their first follow-up list
- Traces to: CAP-022.FR1@APP-desktop-agent, CON-021, CON-022, CON-025, EPC-036.AC1, ...
- Release fit: cannot tell for 2027-02-02.

Checkpoint

docs/work/tickets.md lists every story with its criteria, size and what it waits on, and each one traces to a goal.

Why this step

The plan is the source of truth and tickets are copies. See breakdown and tickets and how every story traces back.

Stuck?
  • A plan that is still moving gets no ticket list. Tickets stops and offers /vela:breakdown.
  • vela tickets check exits 1 when it flags something. That's a result, not a failure.
  • vela export jira-csv --out epics.csv writes one row per epic for Jira's CSV import. Nothing is read back.

Step 13 of 13 · 2 min

What's next

Where to go from here

You've followed one sentence to tickets. A real plan keeps going: new questions arrive, answers change pages, and teams challenge boundaries.

  • Ask the plan: /vela:ask answers from the pages alone and says "Not recorded" when they're silent. /vela:find points to where something is.
  • Fill the gap this demo left: /vela:allocate gives each requirement an owning app. vela next suggests it first on the Heron plan.
  • Keep it honest: vela check before each pull request, vela health for stale pages, vela upgrade after a W717 warning.
  • Read why it works this way: How vela thinks and the user guide.

What you should see

vela next on the Heron copy still says:

vela next: for the whole plan: decide which app owns List my open follow-ups (CAP-022.FR1), with /vela:allocate. It is not decided yet and no app has taken it, so no team owns it yet.

Checkpoint

You can name the next session you'd run on your own plan, and why vela next suggests it.

Stuck?
  • W717 means the plan's rule book differs from the installed vela's. Run vela upgrade, check git diff CONVENTIONS.md and commit.
  • A challenge to a boundary: a team lead runs /vela:challenge. It opens a pull request that stays red on purpose until you answer.
