# What each page of a boundary session holds

Read by boundary in section 4, when it writes a confirmed sheet. `vela check` finds a missing field (E103 and its neighbors), so this is the checklist, not the only guard. Every opening paragraph and every line of prose below is written in the house voice (`house-voice`: the plan's examples, after `voice/VOICE.md` when it exists).

- **The app page:** fill the stub `vela add app-stub` wrote: replace its stub line, set `state: assumption`, and add `sources`. When the user gave where the code and wiki live, add `links: {Repo: <url>, Wiki: <url>}` with the labels they used and exactly their URLs, or a key where `.vela.yaml` has a `link_templates` entry for the label (`vela conventions "Links out of the vault"`). No answer, no `links:` line. `sources` lists every `SRC-nn` the lines rest on and, for lines resting on a decided item or the user's words, the session id of the grill or of this session, so the page never lists none. Keep `stage` no higher than the pages meet: `vela ladder` shows the marked stage beside the one they meet. "Does" and "does not" become its opening paragraphs. An app that already had a page before this session keeps it: change only the lines the user confirmed.
- **Containers:** the table `| Container | Job | Contracts served or used | Proposed by | State |`, every State `assumption`.
- **Contracts it provides:** `vela add contract` writes the heading and the required bullets on this page. Under each, add the case table the lead confirmed (`| Case | When | Status | Answer | Emits | Sets |`, one row per answer, including the turn-downs and failures) with the `**Auth:**`, `**Can time out:**` and `**Retries:**` bullets for what the lead said. A row the lead did not confirm is not written.
- **Contracts it consumes:** add the app to the `**Consumers:**` bullet of each contract it consumes, on the provider's page. A provider outside the initiative with no page gets its contract on this app's page with a `**Provider:**` bullet. That bullet is always a link to the outside party's page (`[[03-context-and-scope#PTY-nn <name>|<name>]]`, typed as `### PTY-nn <name>` under `## Outside parties` if the lead has named it and it has no entry yet), never a sentence about who supplies it ("the pilot user, on their own machine"). If the lead cannot say who the provider is, add an open question that asks (`vela add unknown`), and leave the contract's provider as that unknown's link. A link the user gave for an outside party or a contract goes in a `- **Links:** [API spec](<url>)` bullet on that party or contract, and nothing is written when they skipped. An `integrated` or `unchanged` app in the initiative with no page gets a slim page as `vela conventions "Pages"` says, no `stage`, holding only the contract it provides, at `fact` with its `**Source:**` when a source describes it, or at `assumption`.
- **What was weighed:** `vela add cut` wrote the cut's `- **Options considered:**` bullet on the building-blocks page. Copy the same bullet, `<the picked cut> (picked); <cut>: rejected, <reason>; ...`, to the app page, its runtime page and under each contract it provides. `vela next` and the grill's GATE-2 read it on the item itself: without it the app goes back to Shape.
- **The runtime page:** `06-runtime/apps/<slug>-runtime.md` with `id: RUN-<slug>`, `type: app-runtime`, `title`, `state: assumption`, the same `owner`, `authored: authored` and `sources`, and the confirmed failure line under `## On failure`.
- **Concern cells:** replace the `unexamined` row `vela add app-stub` wrote on each concern page with the confirmed state. A line with no yes keeps `unexamined`: it claims nothing. An `unknown` cell links its unknown.
- **Capabilities:** link each capability the app delivers from the app page, using the page `/vela:requirements` wrote. Only when no page exists, write each confirmed capability as `capabilities/CAP-nnn-<slug>.md`, with `id`, `type: capability`, `title`, `state: assumption`, `owner`, `authored: authored`, `origin: proposed`, its `change`, and opening prose saying what the business can do with it. Link it from the app page and from `04a-capability-delta.md`, one line each. A capability that already has a page gets only the link.
- **Flows:** each confirmed journey as `06-runtime/flows/FLO-nnn-<slug>.md`, with `id`, `type: flow`, `title`, `state: assumption`, `owner`, `authored: authored`, `sources` and `capabilities`, opening prose saying who does what and why, then `## Steps`, a numbered list, one line per step (more than about seven steps are grouped under subheadings), linking the capability or contract it uses by its name. A step that hands something between two lanes starts with its confirmed sender and receiver, `[[booking-building-blocks|Booking]] → [[payments-building-blocks|Payments]]: sends the opaque order ID over [[booking-building-blocks#CON-005 Order identity|Order identity]].` (`vela conventions "Flow steps"`); the arrow names both ends, so no reader has to guess the direction from the verb. An outside party is named by its name or its party page. A journey that already has a page gets only the lines the user confirmed. Ask once per flow, in plain words, which capability the journey serves ("Which of these does the reader get out of this journey: ...?", naming the capabilities), and record the answer as `capabilities: [CAP-nnn]`, the primary one first; the explorer groups its flow picker by it. If the initiative has no capability pages yet, leave the field out and do not invent one; when you edit a flow later, keep it current. Link each flow from the runtime page of every app it names, and from `06-runtime/06-flows.md`.
- **Scope:** the app in the apps-in-scope list on `03-context-and-scope.md`, linking its page.
